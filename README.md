# Игровая платформа-трекер (Микросервисы)

Учебный проект: микросервисная система для отслеживания игровой активности (что-то вроде легкого аналога Steam). Платформа позволяет пользователям добавлять игры в библиотеку, трекать свои игровые сессии и получать очки, на основе которых строятся глобальные лидерборды.

## Команда и распределение ролей
* **Артём Лебедев (Team Lead / Architect):** Проектирование архитектуры и gRPC-контрактов, базовая реализация User & Catalog Service, ревью кода, сведение документации.
* **Глеб Попов (Backend Developer):** Реализация бизнес-логики Tracking Service, защита от состояний гонки (Serializable транзакции), покрытие системы юнит-тестами (xUnit).
* **Алина Капленко (DevOps / SLA):** Настройка инфраструктуры (Docker Compose), внедрение паттернов отказоустойчивости (Polly Circuit Breaker) и интеграция метрик (prometheus-net) для контроля SLA.

## Технологический стек
* **Бэкенд:** C# (.NET 8/9)
* **База данных:** PostgreSQL
* **Взаимодействие:** REST API для внешних клиентов, gRPC для общения сервисов между собой
* **Инфраструктура:** Docker, Docker Compose
* **Мониторинг и отказоустойчивость:** prometheus-net, Polly

## Структура проекта
Исходя из требований к размеру команды (3 человека = 2 сервиса), мы физически делим систему на два микросервиса, объединяя смежные доменные области:
1. **User & Catalog Service:** берет на себя управление пользователями, аутентификацию, общий каталог игр и личные библиотеки.
2. **Tracking Service:** отвечает за учет игровых сессий, тайминги, начисление очков и генерацию рейтингов.

## Инструкция по запуску

Для развертывания инфраструктуры баз данных используется Docker Compose. Сами микросервисы запускаются через стандартный .NET CLI, поэтому привязка к конкретной IDE не требуется.

### 1. Подготовка баз данных
Убедитесь, что у вас установлен и запущен Docker. В корневой директории проекта выполните команду:
```bash
docker-compose up -d
```
Docker автоматически поднимет два независимых контейнера PostgreSQL:
* **user-db** (порт 5432) — база данных для профилей и каталога.
* **tracking-db** (порт 5433) — база данных для игровой статистики.

### 2. Применение миграций
Перед первым запуском необходимо создать таблицы в базах данных. Откройте терминал и выполните команды по очереди:

Для сервиса каталога:
```bash
cd GamePlatform/UserCatalogService
dotnet ef database update
```

Для сервиса трекинга:
```bash
cd ../TrackingService
dotnet ef database update
```

### 3. Запуск микросервисов
Так как сервисы общаются друг с другом по сети (gRPC), они должны работать одновременно. Для этого понадобятся два окна терминала.

**Терминал 1 (User & Catalog Service):**
```bash
cd GamePlatform/UserCatalogService
dotnet run
```

**Терминал 2 (Tracking Service):**
```bash
cd GamePlatform/TrackingService
dotnet run
```

После успешного запуска в консоли появятся адреса (вида `https://localhost:XXXX`). Перейдите по этим адресам, добавив в конец `/swagger`, чтобы открыть удобный интерфейс для тестирования API. Эндпоинты со сбором метрик (SLA) доступны по адресу `/metrics`.

### 4. Запуск тестов
В проекте реализовано покрытие бизнес-логики юнит-тестами с использованием xUnit и In-Memory базы данных. Для запуска выполните:
```bash
cd GamePlatform
dotnet test TrackingService.Tests/TrackingService.Tests.csproj
```

## Архитектурные решения и обеспечение SLA (Этап 4)

Для обеспечения доступности системы на уровне **99%** и удержания **p95 < 300ms** были реализованы следующие механизмы:

1. **Изоляция сбоев (Circuit Breaker & Retry):** Межсервисное взаимодействие реализовано через gRPC. На клиенте (`TrackingService`) настроены политики отказоустойчивости `Polly`. При недоступности `UserCatalogService` система делает 3 попытки (Retry), после чего обрывает цепь (Circuit Breaker) на 30 секунд. Это защищает трекер от исчерпания пула потоков (Thread Pool Exhaustion) и позволяет мгновенно возвращать HTTP 503 Service Unavailable.

2. **Защита от состояния гонки (Race Condition):** Старт игровой сессии обернут в транзакцию с уровнем изоляции `Serializable`. Это на уровне СУБД PostgreSQL гарантирует, что пользователь физически не сможет создать две активные сессии одновременно при параллельных запросах.

3. **Мокирование внешних систем:**
   Интеграция с внешним провайдером лицензий имитируется в `LibraryController`. Реализован генератор искусственных сбоев (10% отказов/таймаутов), который перехватывается паттерном Retry, гарантируя корректный ответ пользователю даже при нестабильности партнера-провайдера.

4. **Метрики и Мониторинг:**
   В оба микросервиса интегрирован пакет `prometheus-net`. Развернуты эндпоинты `/metrics`, которые в реальном времени собирают гистограммы длительности HTTP-запросов (для контроля p95) и счетчики ошибок (для контроля 99% SLA).
